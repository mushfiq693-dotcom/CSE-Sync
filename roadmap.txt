# TECH STACK (FIXED — do not substitute)

* **Framework**: Next.js 15 (App Router), TypeScript
* **Styling**: Tailwind CSS + shadcn/ui
* **Animation**: Framer Motion
* **Backend/DB**: Supabase (Postgres + Supabase Auth + Supabase Storage)
* **Auth**: Supabase Auth for credential handling and session management. Do not hand-roll password hashing or session tokens — use Supabase's built-in mechanisms.
* **File storage**: Profile pictures go in Supabase Storage (a dedicated bucket, e.g. `profile-pictures`). Enforce a max file size (2MB) and allowed types (jpg, png, webp) at both frontend and backend/storage-policy level.

Do not introduce any other framework, ORM, or auth library without explicit confirmation.

# CORE PRODUCT CONCEPT

The platform will contain information about:

* Current CSE Students
* CSE Alumni

The website will work primarily as a **public Student & Alumni Directory**.

Normal visitors do **not** need to create an account or sign in.

Only approved users will be allowed to enter and manage student/alumni information.

---

# USER ROLES

There will be exactly **two roles** in the system:

## 1. Admin

Admin is responsible for:

* Approving user registrations
* Managing approved users
* Managing student/alumni information
* Adding student/alumni profiles
* Updating student/alumni profiles
* Deleting student/alumni profiles when necessary

Admin should have full access to the management functionality.

---

## 2. Approved User

An Approved User is a registered user whose account has been approved by an Admin.

Approved users can:

* Sign in
* Add Student profiles
* Add Alumni profiles
* Update **any** Student profile (not limited to profiles they created)
* Update **any** Alumni profile (not limited to profiles they created)

This is intentionally **shared edit access** — any approved user can edit any profile. `created_by` always reflects the original creator regardless of who last edited it; `updated_by` always reflects the most recent editor. This history must never be overwritten to hide who actually made a change.

They cannot approve other users.

They cannot manage system-level settings.

They cannot access Admin functionality.

They cannot delete profiles (deletion is Admin-only).

---

# PUBLIC VISITOR

A normal website visitor does NOT need:

* Sign up
* Sign in
* Account
* Approval

They can directly visit the website and:

* View all students
* View all alumni
* Search students/alumni
* Browse by session/batch
* View individual profiles
* Sort students/alumni by roll

The directory should be publicly accessible.

---

# AUTHENTICATION FLOW

## Registration

The registration page will contain ONLY:

* Name
* Email
* Student ID
* Password

After registration:

`Registered → Pending Approval → Admin Approval → Approved User`

Until approval, the user cannot sign in.

After Admin approval:

`Approved User → Can Sign In`

Do not automatically approve registrations.

**Duplicate/edge-case handling:**
* Email must be unique across the `users` table at all times (pending, approved, or rejected).
* If a registration is **rejected**, delete the pending user record entirely rather than keeping a "rejected" status. This allows the same email to register again later. Do not keep a rejected-user table or history — that would be unnecessary audit complexity per the "what not to build" rules.
* If an Admin attempts to approve/reject a user that no longer exists (already handled), return a clear error rather than failing silently.

---

# LOGIN FLOW

Only approved users and admins can sign in.

If a pending user attempts to sign in:

> "Your account is waiting for admin approval."

If an approved user signs in:

→ Redirect to the appropriate dashboard.

Admin:

→ Admin Dashboard

Approved User:

→ User Dashboard

---

# IMPORTANT AUTHORIZATION RULE

Do NOT rely only on frontend role checking.

Every protected backend endpoint must verify:

1. Authentication
2. User approval status
3. User role
4. Required permission

A normal public visitor must never be able to access protected management APIs.

An Approved User must never be able to access Admin-only APIs.

Implement this via Supabase Row Level Security (RLS) policies on every table, in addition to server-side route checks — do not rely on RLS alone or API-layer checks alone; both must independently enforce the rule.

# PROFILE DATA

Each Student/Alumni profile should contain ONLY the following information.

## Basic Information

* Name
* Student ID — unique **within its own role category** (i.e., unique among students, and independently unique among alumni). A student who graduates and becomes an alumni record reuses the same Student ID; do not treat this as a collision.
* Session / Batch
* Roll Number — an integer, unique **within a given Session/Batch** (not globally unique). Two different sessions may both have a Roll 12.
* Profile Picture
* Student/Alumni Status

## Status Badge

Current students must have a clear visual indicator such as:

**ACTIVE STUDENT**

Alumni must have:

**ALUMNI**

The badge/status indicator should be clearly visible on the profile.

Do not use unnecessary status categories.

---

# CONTACT & SOCIAL INFORMATION

* Phone Number
* Facebook Profile Link
* Instagram Profile Link
* LinkedIn Profile Link

These fields are **optional**.

## Current Workplace / Employer

Store the current workplace/employer.

## Workplace Details

Include relevant information such as:

* Company Name

Do not create an unnecessarily complicated employment-management system.

---

# LOCATION INFORMATION

* Home District

---

# EDUCATIONAL BACKGROUND

Store:

* Schools attended before university
* Colleges attended before university

Keep this simple (plain text fields, not a separate normalized table).

---

# AUDIT INFORMATION

Every Student/Alumni profile must keep basic information about who created and updated it.

Display:

**Created by: [Approved User/Admin Name]**

If the profile has been updated:

**Updated by: [Approved User/Admin Name]**

The system should automatically store:

* Created By (user id, resolved server-side from the authenticated session — never trust a frontend-submitted value)
* Created At
* Updated By (user id, resolved server-side, updated on every edit)
* Updated At

Do NOT add unnecessary audit/history functionality beyond this — no version history, no changelog, no diff tracking.

---

# DIRECTORY ORGANIZATION

## Student / Alumni Separation

Users should easily distinguish:

* Current Students
* Alumni

---

## Session / Batch Organization

Students and alumni should be grouped/filterable by:

**Session / Batch**

Example:

* CSE 11
* CSE 12
* CSE 13
* CSE 14
* CSE 15

Sessions live in their own `sessions` table (id, label, sort_order) rather than being hardcoded. Admin can add new sessions as needed through a simple mechanism (does not need its own dedicated UI section — can be part of the profile add/edit form, e.g. "add new session" inline).

---

## Roll-wise Sorting

Students/alumni within a session should be sortable by:

**Roll Number**

Roll Number is stored as an integer, so sorting is naturally numeric (1, 2, 3, ... 10, 11 — not lexicographic like "1, 10, 11, 2"). Default sort is ascending roll number within the selected session.

---

# SEARCH & FILTER

Implement simple but efficient search.

Users should be able to search by:

* Name (case-insensitive, partial match)
* Student ID (case-insensitive, partial match)
* Roll (exact or partial numeric match)

Filters:

* Student / Alumni
* Session / Batch

Sorting:

* Roll Number (ascending, default)

Do not add unnecessary advanced filtering unless required later.

# PHASE 2 — DATABASE DESIGN

After the architecture is approved, design and implement the database in Supabase.

The database must support:

* Admin users
* Registered users
* Pending users
* Approved users
* Student profiles
* Alumni profiles
* Sessions/Batches
* Profile ownership/creation information
* Profile update information

Design the schema carefully.

Use:

* Primary keys
* Foreign keys
* Unique constraints (email — global; student_id — unique within role category; roll_number — unique within session)
* Appropriate indexes (session_id, roll_number, name for search/filter/sort performance)
* Required fields
* Optional fields (contact/social fields)
* Appropriate enums/status values (user approval status, job status, student/alumni status)
* Created timestamps
* Updated timestamps
* Row Level Security (RLS) policies enforcing the permission matrix at the database layer

Avoid unnecessary tables. Avoid unnecessary normalization. The database should be **simple but properly structured**.
